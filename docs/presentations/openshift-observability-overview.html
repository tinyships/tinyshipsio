Monitoring & Metrics

SHIPS BY DEFAULT

What Ships on Day 1

The Cluster Monitoring Operator (CMO) deploys everything in openshift-monitoring:

Collection & Storage

  • Prometheus (2 replicas, HA)
  • kube-state-metrics
  • openshift-state-metrics
  • node-exporter (DaemonSet)
  • 15-day default retention

Query & Routing

  • Thanos Querier (2 replicas)
  • AlertManager (2 replicas)
  • Prometheus Adapter (HPA)
  • Telemeter Client
  • Observe console (dashboards + alerts)
Default storage is emptyDir (ephemeral). Configure persistent volumes for production.

User Workload Monitoring

MUST ENABLE — one ConfigMap, cluster-admin required

apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true

Adds to openshift-user-workload-monitoring:

  • Prometheus — scrapes ServiceMonitor/PodMonitor in user namespaces
  • Thanos Ruler — evaluates PrometheusRule resources
  • Prometheus Operator — manages the user-workload stack

Default retention: 24 hours (configurable). Does not require cluster-admin for day-to-day use after enabling.

Pipeline Filters

FilterPurpose
DropDrop entire records based on field matching

Filters apply sequentially. A dropped record does not reach later stages.

Log Storage: LokiStack

LokiStack (current)

  • Object storage backend (S3, GCS, Azure, ODF)
  • Built-in multi-tenancy via gateway
  • OpenShift RBAC enforced automatically
  • LogQL query language
  • Console UI via Cluster Observability Operator

Elasticsearch REMOVED

  • Local persistent volumes
  • No native multi-tenancy
  • Kibana removed in Logging 6.0
  • ES Operator removed Nov 2025
  • Migrate to LokiStack

Alerting

ALERTMANAGER SHIPS BY DEFAULT

AlertManager Architecture

Platform Alerts

  • Pre-configured rules for cluster health
  • Managed by CMO — not editable
  • etcd, API server, node pressure, etc.
  • Evaluated by platform Prometheus
  • DEFAULT

User-Defined Alerts

  • PrometheusRule in user namespaces
  • AlertmanagerConfig for routing
  • Namespace-scoped — no cluster-admin
  • Evaluated by Thanos Ruler
  • REQUIRES enableUserWorkload

Enabling User Alert Routing

apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
    alertmanagerMain:
      enableUserAlertmanagerConfig: true

Two flags:

  • enableUserWorkload — deploys user-workload Prometheus + Thanos Ruler
  • enableUserAlertmanagerConfig — allows AlertmanagerConfig CRs in user namespaces

Without the second flag, alerts fire but cannot be routed to custom receivers.

Supported Receiver Types

Console UI Support

  • Email
  • Slack
  • PagerDuty
  • Webhook
  • Microsoft Teams

YAML-Only Configuration

  • Discord
  • OpsGenie
  • VictorOps / Splunk On-Call
  • SNS
  • Telegram
  • Jira
  • Pushover, WeChat, Webex
  • Rocket.Chat, Mattermost

All receiver types work via AlertmanagerConfig CR (v1beta1) or the alertmanager-main secret.

Alert Flow

PrometheusRule → Thanos Ruler evaluates → alert fires → AlertManager routes → receiver delivers

Network Observability

REQUIRES OPERATOR INSTALL — included at no extra cost

What It Provides

  • eBPF-based flow collection — DaemonSet, no router/switch dependency
  • Kubernetes metadata enrichment — pod, namespace, node, service
  • DNS tracking — request/response correlation
  • NAT/SNAT/DNAT flow correlation (GA in 1.8)
  • Prometheus metrics for alerting
  • LokiStack integration for flow log queries
  • Console UI — traffic table, topology views, dashboards
  • Health alerts (GA in 1.11)

Sampling: 1 in 50 flows by default. Can run without Loki in Prometheus-only mode.

Power Monitoring

TECHNOLOGY PREVIEW — bare metal only

  • Kepler (Kubernetes Efficient Power Level Exporter)
  • eBPF-based agent reads CPU/DRAM power via RAPL or Redfish API
  • Estimates per-container power from CPU time percentage
  • ML-based estimation when hardware counters unavailable
  • Prometheus metrics: kepler_node_power_total, kepler_pod_power_total
  • Dashboards in Observe console

Not supported under production SLAs. Most cloud vendors do not expose power management subsystems.

Ops Checklist

What you need to configure as an operations team

Day 1 — Must Do

  1. Configure persistent storage for platform Prometheus
    Default is emptyDir — metrics are lost on pod restart
  2. Enable user-workload monitoring
    ConfigMap in openshift-monitoring — one-time cluster-admin action
  3. Install Logging Operator + Loki Operator
    No logs are collected until you do this
  4. Create ClusterLogForwarder
    Define what to collect, where to send — nothing flows without it
  5. Configure alert receivers
    Platform AlertManager has no receivers configured by default

Day 2 — Should Do

  1. Install Cluster Observability Operator
    Logging UI, tracing UI, Perses dashboards, Korrel8r correlation
  2. Set up remote write for long-term metrics retention
    Default Prometheus retention is 15 days
  3. Install Network Observability
    Included at no extra cost — eBPF flow collection + topology views
  4. Install OpenTelemetry + Tempo
    If your applications need distributed tracing
  5. Grant RBAC roles to dev teams
    monitoring-rules-edit, alert-routing-edit, monitoring-edit

Key RBAC Roles

RoleGrants
monitoring-rules-viewRead PrometheusRule in a project
monitoring-rules-editCreate/modify/delete PrometheusRule
monitoring-editCreate ServiceMonitor, PodMonitor, PrometheusRule
alert-routing-editCreate/modify/delete AlertmanagerConfig
cluster-monitoring-viewRead all platform metrics (cluster-wide)

Dev teams get monitoring-rules-edit + alert-routing-edit. SRE/ops gets cluster-monitoring-view.

Summary

OpenShift ships a production-grade metrics and alerting stack on day 1.
Logging, tracing, and network observability are one operator install away.
Every signal type supports multiple output protocols for integration with existing tooling.

All components are operator-managed and upgradeable in place.
